# Shop API

REST API для управления клиентами, товарами, поставщиками и изображениями.
Проект запускается в Docker Compose окружении с PostgreSQL, nginx и pgAdmin. Основной упор сделан на чистую архитектуру, OpenAPI-документацию, миграции базы данных, reverse proxy, HTTPS, кэширование и балансировку backend-инстансов.

## Возможности

* REST API с методами GET, POST, PUT, PATCH, DELETE

* Эндпоинты для клиентов, товаров, поставщиков и изображений

* Работа с JSON и application/octet-stream

* Получение параметров из path, query и тела запроса

* Опциональная пагинация:
    * товары и поставщики: limit, offset
    * клиенты: limit, offset, name, surname
    
* Валидация данных на уровне HTTP-слоя, service-слоя и базы данных

* Транзакционные операции, затрагивающие несколько таблиц: создание клиента, поставщика и товара, смена адреса, добавление изображения к товару. При ошибке в любой вложенной операции изменения откатываются целиком

* Уникальный constraint на адрес и дедупликация: повторное сохранение той же тройки (country, city, street) возвращает существующую запись, дубликаты не создаются

* Ограничение остатка товара constraint'ом CHECK и код 400 при попытке уменьшить остаток больше, чем доступно

* Единый формат ошибок и полное соответствие HTTP-кодов бизнес-смыслу

* Полное OpenAPI-описание с примерами, структурами и кодами ошибок

* DTO для API, DAO для базы данных и мапперы между слоями

* Паттерн Repository через интерфейсы репозиториев

* PostgreSQL-миграции, внешние ключи, constraints и триггер для обновления updated_at

* Dependency injection через Uber Fx

* Graceful shutdown через fx.Lifecycle

* Интеграционные тесты на реальном Postgres в Docker (testcontainers), покрывающие транзакционность, дедупликацию адресов под нагрузкой, лимит остатка и коды ошибок

## Инфраструктура

Проект полностью запускается через Docker Compose. В окружении поднимаются:
* PostgreSQL
* основной backend-инстанс
* два read-only backend-инстанса
* Nginx
* pgAdmin

Nginx используется как единая точка входа и выполняет:
* reverse proxy
* маршрутизацию
* раздачу статики
* HTTPS с самоподписанным сертификатом
* gzip-сжатие
* кэширование GET-запросов
* балансировку GET-запросов между backend-инстансами с весами 2:1:1
* проксирование pgAdmin по /admin
* выдачу статуса Nginx по /status

## Обработка ошибок

Ошибки API возвращаются в едином формате:

```json
{
  "error": "..."
}
```

Соответствие кодов ответов бизнес-смыслу:

| Код | Когда |
| --- | --- |
| 200 / 201 / 204 | успешный запрос |
| 400 | ошибка валидации на уровне HTTP-слоя, service-слоя или базы данных, в том числе `insufficient stock` |
| 404 | сущность не найдена |
| 500 | внутренняя ошибка; клиенту возвращается `internal server error`, детали пишутся только в логи API |

Внутри API ошибка не теряется: каждый слой оборачивает её через `fmt.Errorf` с `%w`, а внешнему клиенту отдаётся уже отфильтрованный ответ через единый обработчик.

## Тесты

Интеграционные тесты поднимают изолированный `postgres:17-alpine` через **testcontainers-go**, накатывают миграции из `migrations/`, собирают приложение (репозитории → сервисы → хендлеры → роутер) и проверяют полный HTTP-путь. Тесты помечены build-тегом `integration`, поэтому обычные `go test ./...` и `go build ./...` их не запускают.

Требуется запущенный Docker. Запуск:

```make test```

Покрытые сценарии: откат транзакций при ошибке вложенной операции, дедупликация адресов (в том числе при конкурентных запросах), лимит остатка товара, коды ошибок 400/404, пагинация с фильтрацией, загрузка/выдача изображения и жизненный цикл удаления.

## Локальный запуск

1. Создать **.env**  
Пример содержится в .env.example. При необходимости изменить значения переменных окружения.

2. Добавить локальный домен  
В файл **/etc/hosts** добавить:  
```127.0.0.1 shop.local```

3. Сгенерировать Swagger документацию
```make swag```

4. Собрать и запустить Postgres  
```make db-build```

5. Применить миграции  
```make migrate-up```

6. Создать readonly-пользователя в Postgres  
```make db-create-readonly-user```

7. Сгенерировать локальный HTTPS-сертификат  
```make generate-local-cert```

8. Собрать и запустить проект  
```make build```

## Локальный запуск без HTTPS

Для разработки без самоподписанного сертификата используйте отдельный `docker-compose.local.yaml`. В локальный стек входят только API и PostgreSQL; nginx, HTTPS, read-only реплики, балансировка и pgAdmin не используются. API доступен напрямую по HTTP на порту **8080**. Проект Compose называется `shop_api_local`, поэтому локальный стек можно запускать параллельно с HTTPS-стеком.

1. Создать **.env** (достаточно скопировать `.env.example`)
2. Собрать и запустить локальный стек: `make local-build`
3. Применить миграции: `make local-migrate-up`

- Swagger UI: http://localhost:8080/api/v1/swagger/index.html
- Остановить стек: `make local-down`
- Остановить и удалить данные: `make local-clean`

## Проверка балансировки, кеширования и сжатия

Для проверки балансировки можно использовать ```make nginx-balancing-test```.
GET-запросы должны распределяться между backend-инстансами в соотношении 2:1:1.

Проверка кеширования осуществляется через ```make nginx-cache-test```.
Начиная со второго ответа заголовок **X-Proxy-Cache** должен иметь значение **HIT**.

Для проверки сжатия запускаем ```nginx-compression-test```.
Ответ должен иметь заголовок **Content-Encoding: gzip**.
